# transit-routing — 요구사항

## 목표

출발지·도착지 좌표가 어디든 동일한 인터페이스로 대중교통 경로를 얻고, 국내/해외 API 차이를
`backend/routing` 안에 가둔다.

## 배경 — 왜 프로바이더를 나누는가

Google Maps 는 전 세계를 커버하지만 **대한민국에서는 도보·자동차·자전거 경로를 공식
미지원**한다(고정밀 지도 반출 제한). 데모 도시가 부산이므로 Google 단독으로는 핵심 기능이
죽는다. 반대로 ODsay 는 국내 데이터가 정확하지만 해외를 다루지 못한다.
자세한 판단 근거는 `docs/DECISIONS.md` 2026-08-27 항목 참조.

## 기능 요구사항

| ID | 요구사항 | 수용 기준 |
|----|----------|-----------|
| TR-1 | 좌표로 프로바이더를 자동 선택한다 | 출발·도착이 모두 국내면 ODsay, 그 외는 Google |
| TR-2 | 국가 간 이동도 실패하지 않는다 | 부산→도쿄 요청이 Google 로 라우팅된다 |
| TR-3 | 두 API 응답을 동일 스키마로 정규화한다 | 어느 프로바이더든 `RouteSegment` 를 반환 |
| TR-4 | 경로 유형 3종을 지원한다 | `fastest` / `fewest_transfers` / `scenic` |
| TR-5 | 캐싱 정책을 프로바이더별로 강제한다 | ODsay는 2회차에 외부 호출 없음 / Google은 디스크에 일절 저장 안 함 |
| TR-6 | 실패를 삼키지 않는다 | 키 미설정·API 오류·경로 없음이 `RouteProviderError` 로 구분되어 전파 |

## 범위 밖

- 실시간 운행 정보·혼잡도 (`docs/DECISIONS.md` 2026-08-21 항목에서 제외 결정)
- 자동차·자전거 경로 — 대중교통 서비스이므로 다루지 않는다
- 요금 통화 변환 — 해외 구간 요금은 현지 통화 값 그대로 보여준다

## 미결 사항

- [ ] Google Directions 가 부산 등 국내 도시에서 대중교통 경로를 반환하는지 실측
      (반환된다면 국내 폴백으로 쓸 수 있는지 검토)
- [ ] `scenic` 을 두 API 모두 근사로 처리 중 — 자체 로직으로 대체할지 결정
- [ ] ODsay 캐시 만료 정책 (현재 무기한)
- [ ] Google 은 캐싱이 금지되므로 호출 수 절감을 Haversine 사전 필터에만 의존한다 —
      화이트리스트 도시 수가 늘 때 호출량이 감당되는지 측정 필요
- [ ] 화이트리스트에 국내 도시가 없으면 ODsay 어댑터를 참조 구현으로만 남길지 결정 (8/30 게이트)
