# PoC 문서 — 모두의 여행 (AI 그룹 여행 플래너)

> 고려대학교 x AWS AI Innovators Challenge (AI Tech Day 2026) 예선 제출물 · KUAWS 팀
> 저장소: https://github.com/leegijun0421/KUAWS

## 1. 한 줄 요약

단톡방 대화를 붙여넣으면, LLM 이 사람별 취향과 절대 조건을 읽고, **가장 손해 보는 사람의 만족도를
최대화**하는 장소를 **실제 대중교통 시간표** 위에 배치해 링크 하나로 공유한다.

## 2. 문제 정의

| 현상 | 근거 |
|------|------|
| 그룹 여행 일정 조율은 카톡·스프레드시트 수작업 | 팀원 5명 전원의 경험, 기존 플래너는 1인 입력 전제 |
| 취향을 평균 내면 아무도 만족하지 않는다 | 정반대 2인 대화(`mocks/chats/03`)에서 평균 1위 = 둘 다 그럭저럭인 장소 |
| LLM 단독 일정은 대중교통을 지어낸다 | 노선·편성 시각·환승은 LLM 이 검증할 수 없는 사실 데이터 |

## 3. 해결 — 핵심 기능 6가지

1. **대화 → 취향**: 단톡방을 화자별로 나눠(규칙) 1회 LLM 호출로 5축 취향·신뢰도·하드 제약·꼭 갈 곳을 추출.
   신뢰도 < 0.6 인 축만 슬라이더로 되묻는다. LLM 장애 시 키워드 규칙으로 폴백.
2. **정규화 maximin 매칭**: 멤버별 적합도를 각자의 최고값으로 정규화한 뒤 최저값을 최대화.
3. **제약 스케줄러**: 실제 편성 시각 기반 배치, 12·18시 식사, 요일별 영업시간, 체력 기반 이동 상한, 막차 경고.
4. **실패 위험도**: 환승 연결 여유(실제 시간표)·영업 종료 여유·식사 피크·최저 적합도 — 객관 지표만.
5. **경치 대안 경로**: 같은 호출의 대안 경로 주변 자연·명소 태그로 점수화, "+N분 경치" 병기.
6. **링크 공유**: 입력 + Place ID 순서만 저장, 열 때 최신 시간표로 재계산(약관 준수).

## 4. 기술 구조

→ [ARCHITECTURE.md](ARCHITECTURE.md) (다이어그램·수식)

- 백엔드 FastAPI · 프론트 React 18 + Vite + Tailwind
- LLM: Anthropic Claude(`claude-sonnet-5`) — `LLMProvider` 어댑터 뒤, Bedrock 교체 가능
- 경로: Google Routes API v2 — `RouteProvider` 어댑터 뒤, 국내 ODsay 참조 구현
- 장소: Google Places API (New) 수집 → LLM 사전 배치 태깅
- **런타임 LLM 호출은 대화 1건당 1회뿐**, 일정 생성은 0회(결정적 알고리즘)

## 6. 실측 결과

### 6-1. maximin vs 평균 — 실데이터(파리 수집본 135곳)

정답지 대화 `02_conflict`(정반대 취향 3인)의 프로필로 후보 순위를 두 방식으로 매겼다
(`python scripts/compare_maximin.py`).

| 지표 | 평균 방식 | 정규화 maximin |
|------|:---------:|:--------------:|
| 상위 10곳 겹침 | — | **0 / 10** |
| 상위 10곳의 "가장 불만족한 멤버" 만족도 평균 (파리) | 48% | **65%** |
| 같은 지표 (타이베이) | 52% | **66%** |

평균 방식 상위권은 한 사람이 매우 좋아하고 다른 사람은 싫어하는 장소로 채워졌다. maximin 은
세 사람 모두 "나쁘지 않은" 장소를 고른다 — 그룹 여행에서 한 명이 소외되는 일을 막는 것이 목적이다.

### 6-4. end-to-end 실측 (9/27, Claude·Google Routes 실호출)

가짜 카톡 대화 5종을 **대화 붙여넣기 → 취향 추출 → 일정 생성(2일) → 공유 링크 열람**까지 끝까지 돌렸다
(`python scripts/e2e_check.py --repeat 3`). 각 대화를 3번씩, 총 15회.

| 대화 | 도시 | 일정 생성 | 공유 열람 | 스톱 | 식사 | 그룹 최저 만족 | 최대 실패 위험 | 편성 시각 있는 탑승 구간 | 공유 일치 |
|---|---|---|---|---|---|---|---|---|---|
| 01 기본 데모 | 파리 | 5.3s | 3.4s | 11 | 2/4 | 56% | 21% | 10/10 | ✅ |
| 02 취향 정반대 | 파리 | 3.8s | 2.9s | 13 | 4/4 | 71% | 19% | 8/8 | ✅ |
| 03 알레르기·시간 제약 | 파리 | 4.4s | 3.1s | 10 | 3/4 | 82% | 25% | 11/11 | ✅ |
| 04 잡담 섞인 대화 | 타이베이 | 3.9s | 3.1s | 13 | 4/4 | 70% | 18% | 10/10 | ✅ |
| 05 정보 부족 | 파리 | 3.1s | 2.6s | 15 | 4/4 | 99%\* | 37% | 9/9 | ✅ |

- **15/15 성공**, 같은 대화를 3번 돌리면 스톱 구성이 **3번 모두 동일**(데모 재현성).
- 버스·지하철 탑승 구간 **48/48** 에 실제 편성 출발·도착 시각이 붙었다 — 시각을 지어내지 않는다.
- 일정 생성 3~6초, 외부 경로 호출은 일정 1개당 8~13회(Haversine 사전 필터로 도보 구간은 호출하지 않음).
- 취향 추출은 첫 호출 1~3초, 같은 대화는 캐시로 즉시.
- \* 05 는 정보가 없어 모든 축이 중간값 → 누구에게나 비슷한 장소라 만족도가 높게 나온다(정상 동작).
- 03 은 모든 날이 11시에 시작했다. 해산물·갑각류 키워드는 식당 이름 기준 제외 필터로 들어갔다(이번 수집본에는 걸리는 이름이 없어 실제 제외 0곳 — 한계는 8절).

| 대화 | 방향 일치 | 저신뢰 축 비율 | 하드 제약 |
|---|---|---|---|
| 01 기본 데모 | 89% (9축) | 53% | ✅ |
| 02 취향 정반대 | 100% (14축) | 27% | ✅ |
| 03 알레르기·시간 제약 | 88% (8축) | 47% | ✅ |
| 04 잡담 섞인 대화 | 100% (5축) | 60% | ✅ |

기준(방향 4/5 이상 · 하드 제약 누락 0 · 정보 부족 대화 저신뢰) **모두 통과** → [EXTRACTION_EVAL.md](EXTRACTION_EVAL.md).
대화에 근거가 없는 축은 추측하지 않고 신뢰도를 낮춰 슬라이더로 되묻는다(05 는 100% 저신뢰가 정답).

### 6-6. 실측으로 고친 것

실제 대중교통 시간은 직선거리 추정보다 길다. 모의 경로에서는 보이지 않던 문제 3개를 실측에서 찾아 고쳤다.

| 실측 증상 | 원인 | 수정 |
|---|---|---|
| 3일 일정 2일차가 2곳에서 끝남 | 상위 후보 3곳이 실제 이동시간으로 모두 거부 | 거부 시 최대 8곳까지 확인(통과하면 1회로 끝나 평소 호출 수 동일) |
| 저녁이 통째로 빠짐 | 관광 이동이 하루 상한을 먼저 다 씀 | 남은 끼니가 있으면 관광 이동은 상한에서 20분 남김 + 식사는 +20분 유예 |
| "84 → 12 환승 여유 4분" | 숫자 노선명만 표기 | "Sèvres - Babylone에서 버스 84 → 지하철 12" |

## 8. 현재 범위와 향후 계획

| 현재 | 향후 |
|------|------------------|
| 알레르기 필터가 음식점 이름 기준 | 메뉴·유형 태그로 확장 |
| 이동 상한 120분 그룹은 실측에서 끼니 1개가 빠질 수 있음(01) | 식당을 먼저 고정하고 관광지를 채우는 2단계 배치 |
| 외부인 사용 테스트 미반영(예선 제출 후 진행) | 지적 사항을 본선 UI 개선 1순위로 |
| 지원 도시 2곳 | 일본용 라우팅 어댑터(NAVITIME 등), 런던·싱가포르·방콕 POI 추가 |
| 명소 체류시간이 유형 기본값 | 장소별 체류시간 수집 |
| 코스 브리핑이 템플릿(절단 1) | `LLMProvider` 로 LLM 브리핑 복원 |
| 택시 대안 없음(절단 2) | `SegmentRoute.alternative` 자리에 재투입 |
