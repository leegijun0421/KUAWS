# 아키텍처

> 초안. 1주차 회의에서 확정한 뒤 갱신한다.
> 최종 발표(10/19)의 "기술 설명의 명확성" 항목이 이 문서에서 나온다.

## 전체 흐름

```
참가자 N명
   │ 자유 텍스트 + 정량 보강
   ▼
[intake]  Bedrock → 취향 축별 값 + 신뢰도
   │  PreferenceProfile × N
   ▼
[scoring] POI 후보 × 그룹 프로필 → 적합도 + 실패 확률 + 멤버별 만족도
   │  PoiScore[]
   ▼
[planner] 제약(시간·이동·식사) 하에서 배치, 최저 만족도를 최대화
   │  ItineraryDay[]
   ▼
[routing] 구간별 실제 대중교통 경로. 경로 유형(최단/환승최소/경치) 분기
   │  RouteSegment[]
   ▼
[share]   링크 생성 → 플랫폼 무관 공유
```

## 왜 LLM만으로는 안 되는가 (기술적 우월성 근거)

| 단계 | LLM 단독 | 우리 방식 |
|------|----------|-----------|
| 취향 추출 | 가능 | LLM 사용 (적합) |
| 그룹 조율 | 평균적·밋밋한 결과 | 최저 만족도 최대화 알고리즘 |
| 장소 선정 | 근거 없는 추천 | 객관 지표 기반 실패 확률 |
| 대중교통 경로 | **불가능** (환각) | 실제 경로 API + 캐싱 |

LLM은 "몇 번 버스를 타고 어디서 환승하는지"를 신뢰성 있게 만들어내지 못한다.
이 지점이 프로젝트의 가장 강한 차별점이다.

## 데이터 흐름과 캐싱

- POI 성향 벡터화는 **배치**로 미리 계산한다 (요청 시 계산 금지).
- 경로 API 응답은 전량 캐싱한다. 캐시 키 = (출발 좌표, 도착 좌표, 경로 유형).
- 호출 전 Haversine 사전 필터링으로 후보를 줄인다.
